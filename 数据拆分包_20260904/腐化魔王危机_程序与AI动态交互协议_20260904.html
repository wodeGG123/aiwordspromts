设计目标

每次调用仍把玩家状态YAML当作完整权威快照，但静态提示词按状态机粗粒度装配：生成事件时装载当前轮数/阶段候选，执行战斗、检定或结算时只装载当前事件。AI不需要收到整局剧情原文，也不能用旧聊天内容覆盖本次输入。

程序装配并保存

固定引擎、世界规则和副本运行包版本及哈希，再保存回合、资源、队伍、道具、圣物、货币、剧情状态、奖励与请求缓存。

AI负责理解与裁决

在副本包边界内选择事件、生成剧情和选项，并让角色真实属性、职业、种族、性格与背景影响检定。

状态可恢复

断线、重试、上下文裁剪或模型切换后，只要重新发送结构化状态即可继续。

权威原则同一事实同时出现在当前输入、旧输出和聊天历史时，始终以当前输入为准。

每次API请求实际发送什么

  1. system消息：严格按“模板专属引擎 → 完整世界规则 → 当前副本上下文 → 最终自检”拼接。
  2. user消息：只发送#本次程序运行态输入和本次完整runtime YAML。
  3. assistant响应：一份无JSON包装的连续YAML正文；禁止Markdown、解释或第二份YAML。
动态不等于未知动态的只有runtime值、候选ID和activeEventId。哪一种引擎模板、哪一种副本上下文、字段条件和拼装顺序都由operation矩阵固定。完整可运行例子位于03_完整流程模拟。

event_output唯一表示法

pending_interaction.event_output固定为上一份已校验“新一轮事件”的完整解析对象，必须包含根层event_details及全部steps/options。它不是字符串、不是摘要，也不能写占位文字。active_event请求依靠它保持玩家看到的选项、角色和场景逐字一致。

resolution_output唯一表示法

pending_interaction.resolution_output只在settle_check与battle_result请求中存在，值分别是上一份已经通过校验的完整“检定”或“战斗事件”解析对象，并保留根层event_details。它不能是result字符串、敌人列表摘录或自然语言摘要。start、next_round、choose和finale不得伪造该字段。

pending.phase在请求时的精确定义

  • start / next_round：pending为null。
  • choose：请求发出时为awaiting_choice。
  • 检定响应被接受后：程序缓存check_result并改为awaiting_settlement_commit，再发送settle_check。
  • 战斗配置响应被接受后：改为awaiting_battle_result；战斗系统产生结果后改为awaiting_settlement_commit，再发送battle_result。
  • 直接结算choose：请求发出时仍是awaiting_choice；AI结算返回后在CAS期间内部转为awaiting_settlement_commit。
  • 结算提交成功：pending清空。

为什么外来角色不需要进入世界规则

世界规则只描述当前世界稳定成立的事实与当地解释方式，通用引擎负责跨世界角色机制，副本运行包描述当前冒险可能遇到的实体与情绪主题；current_team描述玩家这次带来了谁。其它世界角色和暂未归属任何已定义世界的角色都能直接进入副本。服务器必须提供真实属性、职业、种族和性格；narrative_profile与来源世界字段有则提供、没有则省略。AI仍能依据人物本身产生对话和检定差异，但只有来源世界明确时才能进一步描写文化对照。

未定义世界不是错误状态origin_world_id与origin_world_name均为独立可选字段。两者都缺失时，不发送空字符串、null、“未知”或临时伪ID；AI不得自动把角色归入当前世界，也不得虚构故乡。

第一项：先把供应商回调规范化为“新增正文”

AI服务返回的每一块数据可能落在字段名、缩进、双引号、转义符甚至一个UTF-8字符中间。前端不得把一次回调当成一行、一句话或一个YAML节点，也不需要额外包装request_id、seq、delta或done。每个AI供应商适配配置必须明确以下一种模式，不允许运行时靠内容猜测。

cumulative_text每次给截至当前的完整正文快照验证新快照以前一快照为前缀，只追加新增后缀前缀不一致说明供应商改写了已生成文字，立即终止本次流

第三项：双缓冲、完整行扫描与模板状态机

rawYaml只做原样累积，任何提取逻辑都不得修改它；lineBuffer只用于寻找LF，兼容LF与CRLF。最低实现只处理已经收到换行符的完整行，EOF时再处理最后一行。每行只解析一次，禁止每到一个token就对半份YAML调用完整解析器。

let rawYaml = "";
let lineBuffer = "";

function feedAddedText(text) {
  rawYaml += text;
  lineBuffer += text;

  for (;;) {
    const lf = lineBuffer.indexOf("\n");
    if (lf < 0) break;
    let line = lineBuffer.slice(0, lf);
    lineBuffer = lineBuffer.slice(lf + 1);
    if (line.endsWith("\r")) line = line.slice(0, -1);
    streamScanner.consumeCompleteLine(line);
  }
}

扫描器按WAIT_ROOT → READ_HEADER → READ_VISIBLE_BODY → ATOMIC_TAIL → EOF推进。第一条非空行必须是event_details:，其第一项必须是template_name；READ_HEADER按当前模板规定的顺序读取且只接受允许的template_name、event_id和scene_name。重复、越序或模板不允许的头字段会关闭本次临时展示。门控通过前，只有模板中本来位于scene_name之前的current_theme等合法可见值可以缓存；门控失败则清空缓存并禁止后续提前展示。进入options、result、combat_start、enemies、summary、story_patch或final_chapter后切到ATOMIC_TAIL，只继续累积原文，不再尝试展示表外字符串。

结算字段的真实层级五模板以实际缩进为准：结算的summary、story_patch与final_chapter都位于event_details内部，所以原子路径分别是event_details.summary、event_details.story_patch和event_details.final_chapter；只有战斗模板的combat_start与enemies位于根层。前端不得按字段名称猜测层级。

npc必须缓存到同一dialogues项的speech完整闭合后再一起发出。遇到非法缩进、重复头字段、未知可见路径、块标量、未闭合或非JSON兼容字符串、单行超过32 KiB时，执行disable_provisional_continue_raw_accumulation：停止本次临时展示但继续收完整原文，绝不猜测或修正文档。整份rawYaml建议设置256 KiB上限，超过后取消请求且不改变状态。

可选升级：字段内部按完整句子展示

最低实现必须支持complete_visible_field，已经能让每个narration和npc+speech依次出现。只有终章content或检定analysis仍显得过长时，才启用sentence_inside_open_scalar：确认合法字段前缀并通过header gate后，在开放双引号内部维护反斜杠、转义和Unicode转义状态，只在“。！？；”等句末标点后释放完整句子；不完整转义、半句话和闭合引号后的内容全部保留。字段闭合时释放尾句。同一rawYaml无论一次到达还是逐字节到达，忽略到达时间后的分片文本、路径、npc与行号序列必须相同。该模式仍是provisional，不能推进状态。

文本安全与范围所有流式文字按纯文本渲染，不执行HTML、Markdown、富文本标签或链接。提取器拒绝YAML块标量、锚点、别名、标签、复杂键和表外路径；模型提示词已经同步禁止这些形式。

第四项：输入后立即反馈并立即发起请求

前端在本地锁定本次操作、生成或取得request_id并冻结请求状态后，必须立即发起AI请求；本地动画与网络请求并行，不允许先播完动画再请求。

操作无需AI即可立即显示同时执行禁止
选择选项高亮并锁定选项，复述玩家已选择的行动text，播放通用行动反馈立即发送choose请求不得预告检定成功、战斗敌人或奖励
战斗结束程序已知的胜利、失败或撤退演出立即发送battle_result请求不得等退出战场动画结束后才请求结算
提交检定保留已选择行动并显示“结果正在显现”等中性反馈立即发送choose请求不得由前端猜测主行动者、属性或result
下一轮/开局当前场景环境动画和中性过渡立即发送next_round/start请求不得本地虚构新场景、NPC或事件主题
终章按程序已确认的成功或失败播放中性转场立即发送finale请求不得提前展示尚未生成的结局细节
本地反馈的数据来源只能使用本次已确认输入：玩家选择的options[].text、程序战斗结果、当前场景和已确认run_status。不得为了掩盖等待而新造一段可能与AI结果冲突的剧情。

第五项：前端完整解析通过后才开放交互和应用状态

前端显示了多少临时剧情都不改变提交条件。前端必须等待原始流结束，解析一次完整YAML，并依据本次请求快照依次检查模板Schema、字段顺序、枚举、事件/资产引用、pending、资源变化、终局、request_id和state_version。只有全部通过，才能把临时剧情确认为最终内容并推进本地状态机。

内容流式阶段完整校验通过后
旁白、对话、analysis、content可以标记为provisional逐段显示转为最终文本并写入本次响应记录
options不显示、不可点击整体校验后一次性显示并创建pending
combat_start、enemies不启动战斗敌人数量、名称与事件池通过后启动
result不推进状态机公式和枚举通过后才能发起settle_check
summary、story_patch、final_chapter不展示为已生效、不修改任何状态同一前端状态事务一次性应用；任一失败则全部不应用
流式失败处理断流、完整YAML非法或业务校验失败时，禁止创建pending、显示选项、启动战斗或应用任何delta。已显示的provisional剧情停在原位并进入“正在确认结果”状态；纯格式修复或受控重试必须冻结已经显示的可见字段。若错误涉及已显示内容的事件、场景或角色语义，不能静默改写，应终止本次展示并给出统一生成失败提示。
最低实现验收条件
  1. 前端rawYaml逐字等于AI连接从开始到EOF或完成回调收到的全部正文。
  2. 首个合法可见字段完成前，不显示AI生成内容；header gate失败时整个响应不展示。
  3. delta_text在UTF-8字符、CRLF、字段名、反斜杠和双引号任意位置切开时，rawYaml和展示结果都不变；合法重复文字不得被误去重。
  4. cumulative_text只追加快照新增后缀；重复快照不重复展示，历史前缀被改写时立即失败关闭。
  5. 同一rawYaml采用整块、任意小块或逐字节输入时，最终rawYaml及语义展示单元必须一致，不能因供应商切片不同而改变句子分段或行号。
  6. 表外字符串路径永不提前展示；npc必须与对应speech成对。
  7. 最低实现以完整可见字段为UI分片，不依赖AI额外输出chunk字段或注释标记。
  8. 块标量、非法缩进、非兼容转义、未闭合字符串或单行超限只关闭provisional提取；未超过总量上限时仍保留原文等待最终解析。
  9. 流式期间断网、取消或YAML尾部非法，state_version、pending、资源和奖励均保持不变。
  10. 完整合法响应的最终展示内容与非流式完整解析结果一致，不能出现重复段落。
  11. options、战斗启动、检定推进和结算应用都只能由前端完整解析与校验成功事件解锁。

新事件场景提交

  1. start/next_round调用时，runtime中的current_scene_id是调用前已提交场景。
  2. AI返回“新一轮事件”，scene_name表示本事件目标场景，可为当前场景或副本连接白名单中的相邻场景；固定主线可以直接锁定其授权目标。
  3. 程序用manifest的scene_name_to_id得到target_scene_id，校验连接关系、事件阶段和固定主线目标。
  4. 通过后创建pending_interaction，写入scene_id/scene_name；同时更新顶层与story_state.current_scene_id，并把新ID去重追加到visited_scene_ids。
  5. 上述场景提交、pending创建与state_version+1必须原子完成，并发生在玩家看到选项之前；若响应非法则不移动场景。
  6. choose、settle_check、battle_result和结算必须使用pending锁定场景，禁止再次移动。

跨世界情境如何进入成功率

  1. 常规/隐藏属性检定先选primary_actor：目标属性最高者；并列时用角色适配和队伍顺序稳定裁决。叙事必须由该角色真正完成关键动作。
  2. 同一主行动者的职业、种族、性格以及已提供的narrative_profile共享一个role_fit_bonus，只能是-2、0、+2，不能按资料项分别累加。缺少narrative_profile时照常检定。
  3. 道具、flag、NPC关系、明确圣物互动等其它来源通常各±2；所有优势与劣势净值限制在-6到+6，同一事实不重复计算。
  4. 背景只能解释行动为何更容易或更难，不能创造表外技能。例：熟悉宫廷礼法可帮助陌生王国谈判；它不能自动赋予开锁或治疗能力。
  5. 第二名队员只有在剧情中确实提供不同来源协助时才可贡献一个+2，不把全队背景无条件叠加。
研发实现量上述角色选择、适配判断和掷点仍由AI完成。程序只需传真实数据、固定种子并缓存响应；无需开发技能标签系统或专用跨界事件系统。

事件链、转折与失败协议

曲折、失败后果与隐藏回收都通过固定story_patch保存事件因果，不增加输入字段或输出模板。程序把字符串状态完整回传，并对终局条件做白名单校验。

转折要改变玩法

有效转折必须改变选项、检定依据、NPC、资源、奖励、后续事件或终局条件，不能只有一段“原来如此”的旁白。

失败可以推进

普通或支线失败会留下资源损失、NPC恶化、路线关闭或不利flag，然后继续下一轮。

严重后果先预警

AI在选项前用世界内信息说明护送目标、唯一出口、倒计时或不可逆风险，但不显示内部等级和概率。

结构化事件、上下文优化与剧情记忆

世界规则和完整runtime YAML始终发送；事件自身以结构化字段声明调度条件和可用资产范围。装配器只读取这些字段，不扫描叙事正文；AI在每个事件自己的core/possible范围内选择实际角色与场景。这样保留AI创作随机性，同时避免角色表、场景表和事件全集反复出现。

新一轮事件的低成本硬过滤

  1. 先用current_round确定P1–P5。
  2. 直接读取每个事件的schedule，过滤阶段不匹配、轮数不在范围以及已经完成的事件。
  3. 第1、4、8、12、17轮分别只装载固定M01–M05；第24轮M06未完成时只装载M06。
  4. 普通轮装载当前阶段的全部随机事件、隐藏事件，以及处于窗口中的M06。
  5. PLAN/HINT、局内道具、路线分、NPC关系、场景细节和叙事适配仍由AI读取完整状态和事件正文判断，程序不重复实现。
保守过滤原则程序只删除“必定不可能”的事件。全局短提纲始终提供M01–M06与H01–H07的一句话方向，使AI仍能铺垫未来；短提纲不授予当前轮生成未装载事件的权限。

角色与场景如何跟随事件裁剪

每个事件在asset_scope中显式给出角色和场景范围。core是事件可以依赖的核心资产；possible是AI可以结合队伍、状态、当前位置和近期重复情况选择的变化池，不要求全部使用。rules_text可以提到不在场的已知角色或地点作为背景信息，但只有本事件asset_scope中的本地角色才能现身、发言、行动或参战，只有其中场景才能成为目标地点。

  1. 对本次included_event_ids逐项读取roles.core、roles.possible、scenes.core和scenes.possible并取传输并集。
  2. 额外装载current_scene_id对应场景，只用于开场位置和迁移连续性；它不会自动进入任一事件的目标场景范围。
  3. 程序按role_id和scene_id直接取得原始资产块，不根据名称、轮数、权重或正文做二次推断。
  4. AI选定event_id后回到该事件自己的asset_scope；其它候选事件带来的资产即使已在传输并集中，也不得借用。
  5. current_team不参与裁剪，仍从runtime完整发送。跨世界或未归属世界的上阵角色因此始终可以参与对话与检定。
随机性仍由AI承担possible池为同一事件准备多个合法角色和场景。AI可以根据current_team、story_state、run_archetype、词缀和近期重复情况选择不同组合；程序只装载与校验范围，不替AI决定具体组合。
结构或资产错误必须失败关闭事件定义缺字段、role_id或scene_id不能回指资产表、current_scene_id非法、schedule与固定轮规则冲突，或事件YAML无法生成时，不允许扫描rules_text补救，也不能使用依赖同一坏定义的完整上下文。程序必须停止本次AI请求并记录配置错误。

当前事件如何继续

接受新一轮事件后，程序除现有pending外还要保存active_event_id和该轮完整新事件输出。后续轻量调用同时发送：当前事件完整YAML、该轮新事件输出、锁定选项、完整runtime YAML以及必要的check_result或battle_result。结算完成后清空当前事件原文，只把story_patch合并入story_state。

const prepared = prepareAdventurePrompt({
  runtimeYaml,
  expectedTemplateName: operation.expected_template_name,
  currentRound: runtime.current_round,
  completedEvents: runtime.story_state.completed_events,
  forcedEventId: operation.forced_event_id,
  currentSceneId: runtime.current_scene_id,
  activeEventId: pending_interaction?.event_id
});

sendToModel(prepared.prompt);
auditLog.context_scope = prepared.contextScope;

每次发送
  • 完整story_state快照
  • 当前队伍、圣物和局内道具
  • 当前资源、场景、词缀与奖励状态
  • 尚未结束的pending_interaction

  • 已经结算事件的完整YAML
  • 战斗过程日志
  • 只影响战斗的圣物数值

事件尚未结算时，程序保留当前新事件输出、选中选项或检定结果。结算完成后，通过story_patch合并为结构化状态，当前事件原文即可退出后续上下文。跨轮转折主要依靠completed_events的真实outcome、稳定flag、NPC状态、悬念和因果笔记延续。

固定上限memory_notes最多24条、unresolved_hooks最多3条、recent_event_ids保留最近5项。程序不需要理解普通笔记语义：超过24条时按最早写入优先裁剪；必须长期保留且参与条件判断的事实应由稳定flag、completed_events或npc_states保存，不能只依赖memory_notes。必要时可额外保留最近1–2轮各100–200字短摘要，但不再发送完整剧情。

受控金币交易

AI可以决定剧情中是否发生金币交易并提出delta，但不能直接修改账号。程序仍负责白名单、余额、上限、幂等和原子提交。

summary:
  - summary: "支付300金币换取黑市账房的钥匙"
  - type: "player_attr"
    gold: -300
同时满足才允许事件骨架明确标记gold_allowed、gold_policy.enabled=true、金额存在于对应白名单、未超过单事件上限和余额；正金币还不能超过gain_limit_remaining。

具体材料、圣物、因缘和卡牌仍不能由AI用金币自由定价或直接购买。若要做商店，程序必须把商品候选、ID和价格作为权威输入。

受控钻石交易

钻石沿用金币的输入和结算方式，但属于更高价值货币，因此默认关闭，并增加“玩家明确知情”和“扣款前确认”两道要求。

diamond: 1260
diamond_policy:
  enabled: true
  allowed_spend_values: [5, 10]
  allowed_gain_values: []
  max_spend_per_event: 10
  max_gain_per_event: 0
  gain_limit_remaining: 0
双重授权

事件必须写明diamond_allowed，且diamond_policy必须允许对应方向和金额。

玩家知情

支出选项必须明确写“消耗N钻石”，不能把金额藏在结算或旁白里。

程序提交

AI只提出delta；程序检查余额、白名单、上限、幂等，并在扣款前执行二次确认。

腐化魔王危机配置目前只有R_P3_BLACK_LEDGER允许可选钻石支出，并且与金币支出二选一；当前没有任何事件授权AI发放钻石。仅填写allowed_gain_values不会自动产生钻石奖励，仍需事件明确写出diamond_allowed=gain。

程序需要解析的AI输出字段

五种模板的根结构保持不变。程序先按event_details.template_name选择对应schema，再校验字段；不要用叙事文本反推业务状态。为支持流式展示，字段顺序必须与模板一致，可见字符串必须使用单行双引号标量，但这些序列化约束不改变任何字段的类型或业务含义。

event_details.story_patch.selected_option_id结算integer玩家实际选项；无玩家选项的系统结算为0。

event_details.story_patch.run_modifier_ids[]结算array<enum>当前绝对配置；固定2项且不同互斥组。

新一轮事件提交规则
  1. 验证request_id未提交、state_version仍匹配，template_name为新一轮事件。
  2. 验证event_id属于副本白名单，满足阶段、前置、完成状态和候选/强制约束。
  3. 把scene_name映射为target_scene_id，验证同场景、连接白名单或固定主线授权。
  4. 验证全部选项字段、可见性、可用性、检定最终难度，以及至少一项available=true。
  5. 创建pending_interaction并锁定event_id、场景和完整事件输出；原子更新current_scene_id、visited_scene_ids并把state_version加1。
  6. 只有上述步骤全部成功才缓存为逻辑request的有效响应、把此前provisional剧情确认为最终内容并向玩家开放选项；完整校验前只能按流式协议展示临时剧情。
story_patch合并规则
  1. 验证completed_event_id等于当前pending event_id。
  2. 验证request_id未提交过，且state_version仍是请求对应版本。
  3. 将completed event追加到completed_events，拒绝重复。
  4. 先应用remove_flags，再添加add_flags；同一flag不得同时出现。
  5. 累加route_delta，结果不得小于0。
  6. 按npc名称覆盖或新增npc state。
  7. 追加memory_notes并按上限裁剪；添加和解决unresolved hooks。
  8. 保存run_archetype和两个run_modifier_ids；已固定后拒绝变更。
  9. 验证summary后计算未钳制资源结果；先判断supply≤0、corruption≥100硬失败，再把两者钳制到0–100；同时独立处理局内道具及受控gold/diamond。
  10. 依据event_id、outcome、成功/失败flag、硬阈值、team_status与终局白名单设置run_status。final_chapter只是AI提案：硬阈值可以把false覆盖为failed；普通defeat不能仅凭true绕过白名单。
  11. 原子提交全部变化、清空pending并把state_version加1；任一校验失败则全部不提交。

错误响应、修复与幂等
  1. operation.request_id是逻辑状态迁移ID；模型供应商的每次实际调用另用程序内部attempt_id，不发送给AI，也不写入五模板。
  2. 只有通过YAML、schema、枚举、引用、资源与状态机全部校验的响应，才能成为request_id的最终幂等缓存。非法原始响应可留审计日志，但不得作为业务回放结果。
  3. AI连接超时或断流且前端尚未取得完整响应时，可用同一逻辑request和同一状态/种子重试；一旦前端已有校验通过的最终缓存，所有重试直接回放。
  4. 纯格式修复必须锁定原响应的event_id、选项、检定result、战斗result、summary数值、奖励触发与story_patch语义，只修YAML引号、缩进、字段位置或枚举拼写。
  5. 新事件尚未在前端展示任何provisional字段，且出现包外event_id、非法场景、非法敌人、无可用选项等语义错误时，允许最多一次受控再生成；状态、request_id、seed和候选完全不变。仍失败则由程序返回维护提示，不要求AI发明第六模板。
  6. 已经发送provisional字段后，格式修复或受控重试必须逐字冻结这些可见字段；如果错误本身涉及已显示的非法事件、场景、角色或结果语义，则不能静默换文，必须终止本次展示并返回统一失败提示。
  7. 检定结果、战斗结果、货币变化、永久奖励触发或已经最终提交的事件不能通过再请求改变。语义修复需要把这些业务值作为冻结约束。
缓存边界“同一request_id直接回放缓存”只指已经通过全部校验的最终响应；绝不能把格式非法或业务非法的第一次输出固化成永久坏缓存。

推荐接入顺序

  1. 把manifest、三个包、结构化事件定义文件、上下文装配入口与完整组合降级资产作为同一发布物；启动时校验兼容ID与全部哈希，并缓存eventDefinitions及ID资产索引。
  2. 创建run时固定引擎、世界规则与副本运行包版本、run_seed、run_difficulty；按副本公式确定run_archetype与2个run_modifier_ids，写入初始story_state；之后禁止静默换包或重算配置。
  3. 每次调用通过prepareAdventurePrompt按expected模板选择上下文；世界包与runtime保持完整，runtime始终最后追加；读取入口导出的streamingDisplayContract初始化前端提取白名单。
  4. start/next_round直接读取eventDefinitions.schedule过滤事件，再合并各事件asset_scope和current_scene_id生成传输白名单；choose/settle_check/battle_result改用active_event_id只装载当前事件YAML。
  5. 按operation表校验必填字段和expected_template_name；冻结request快照后立即调用AI，与前端本地反馈动画并行。
  6. 前端直接累积AI原始YAML流，并仅显示通过header gate和字段白名单的provisional纯文本；同request_id只接受已经通过完整校验的最终结果。
  7. 新事件先验证完整YAML、字段顺序、event_id、目标场景、连接、选项和候选，再原子创建pending、提交场景并开放选项；战斗/检定/结算沿用锁定场景。
  8. 结算时验证模板枚举、敌人数、资源范围、pending关联和终局白名单；按未钳制资源判断硬阈值并钳制后，以state_version做CAS原子提交。
  9. 结算时把story_patch合并为story_state，而不是累积发送历次story_patch；随后清空active_event原文，只在未结算交互中保留当前事件必要输出。
  10. 收到900050/900060/900061立即拦截、生成具体资源并弹窗；下一请求再将标准资源名放入revealed_pending_rewards。
  11. 终局先完成程序奖励落库并生成granted_permanent_rewards，再调用finale让AI写自然终章。
不能依赖AI自证包版本、哈希、余额、战斗结果、奖励抽取、永久资源落库、幂等和终局白名单始终由程序校验。AI输出合法YAML也不等于可以直接入库。
